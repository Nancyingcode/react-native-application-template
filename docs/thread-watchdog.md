# 线程卡死监控

`ApplicationProvider` 挂载后通过 `startThreadWatchdog` 启动 Android / iOS 原生监控模块，卸载或 React 实例销毁时清理。默认仅 Release（`!__DEV__`）启用；需要本地故障注入时，可临时给入口传入 `true`。不新增依赖。

## 检测规则

- JS Thread 每 1 秒通过原生模块发送心跳；独立原生后台线程检查心跳是否超过 5 秒未到达。
- Native Main Thread 每 1 秒接收一次原生探针，后台监控线程判断是否超过 5 秒未确认。最多保留一个待确认探针，避免卡死时无限堆积。
- 两个线程分别计时，每次连续无响应只记录一次，恢复后允许记录下一次卡死。阈值为 Android / iOS 文件中的 `thresholdMs`，修改时应保持一致。
- 使用单调时钟计时，原生生命周期在后台/非活跃状态暂停，恢复前台重新计时。Android 额外在原生调试器连接时重置计时。
- 原生监控线程会输出 `ThreadWatchdog` 系统日志，并原子保存最近 40 条未消费记录，排除系统备份。持久化失败写系统日志，内存中的记录仍可读取。
- JS 每 5 秒读取记录，通过现有 `Monitor.capture` 写日志和 `app_error` 埋点，`source=thread_watchdog`，`thread=js|native_main`。启动时也读取上次进程留下的记录。

记录包含唯一 ID、检测时间、阈值和检测时已无响应时长。Android 附带检测时获取的主线程 Java 栈；iOS 不采集线程栈。`durationMs` 是检测时长，不是最终卡死总时长。

## 能力边界

这是“长时间无响应”检测，不证明发生死锁，也不会自动重启或杀进程。首个 Provider effect 之前的启动卡死、进程整体被暂停、系统提前杀进程、监控线程本身无法运行均不保证记录。主线程阻塞也可能间接阻止 RN 定时器/桥接工作，因此两个线程同时告警不代表两个独立根因；JS 心跳超时也可能来自原生模块调用队列拥塞。

原生记录交给 `Monitor.capture` 后才按 ID 清理；这不代表服务端已经收到，当前埋点服务的用户同意开关及内存队列规则保持不变。不保证端到端恰好一次投递；可使用报告 ID 去重。

## 设备验收

使用专门测试构建临时开启监控，故障注入代码不要进入正式包。

1. 前台正常运行至少 15 秒，确认无告警。
2. 在 JS 操作回调里阻塞约 8 秒；期间查看原生 `ThreadWatchdog` 日志应有 `js` 记录，恢复后确认 `monitor.capture` 收到同一个 ID。
3. 在 Android 主 Looper / iOS main queue 的测试回调里阻塞约 8 秒；确认 `native_main` 被记录。同次阻塞持续更久时不应反复新增记录；恢复后再次阻塞应新增 ID。
4. 后台停留超过 10 秒，回前台应获得新的 5 秒窗口，且后台停留不作为卡死记录。
5. JS 持续阻塞且原生日志已记录后终止进程，再启动，确认本地记录能被读取；消费后再启动不重复读取已确认记录。
6. 卸载 Provider 或重新加载 React 实例，确认旧定时器和原生探针被清理。

Jest 覆盖 JS 心跳、消费顺序、失败重试、在途读取与销毁；原生生命周期、故障注入、进程重启须在 Android / iOS 设备或模拟器验证。
